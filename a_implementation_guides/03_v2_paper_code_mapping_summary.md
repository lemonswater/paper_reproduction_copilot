# 03. V2 论文-代码证据化映射学习总结

## 这一阶段的目标

这一章的重点是把“论文里提到的方法模块”和“代码仓库中的具体实现”联系起来，而且这种联系不能只靠猜。

输入来自前两个阶段的结构化结果：

- `method_modules`
- `repo_map`

输出则是：

```text
outputs/paper_code_mapping.json
outputs/paper_code_mapping.md
```

简单说，这一阶段解决的是“如何把论文模块映射到可能对应的代码文件、类和函数，并且给出证据与置信度”的问题。

## 本阶段新增了什么能力

相较于 V0 的论文结构化阅读和 V1 的仓库地图构建，V2 开始真正打通“论文”和“代码”之间的桥：

- 根据论文模块生成搜索关键词。
- 在本地仓库中搜索候选代码文件。
- 读取有限代码片段，避免盲读整个仓库。
- 让 LLM 基于论文模块、搜索结果和代码片段做结构化映射。
- 输出带证据、带置信度、带待确认问题的 mapping 结果。

这意味着项目不再只是分别“理解论文”和“理解仓库”，而开始具备“把两边对上”的核心能力。

## 为什么这一阶段很重要

这一章其实是整个项目里最能体现工程思维和 Agent 设计水平的阶段。

如果没有论文-代码映射，后面的问题都会很难：

- 实验计划不知道该参考哪些脚本和配置。
- 日志调试时很难定位论文里的某个模块对应代码的哪部分。
- 即使找到了候选文件，也无法解释“为什么是它”。

所以 V2 的关键不是“找一个看起来像的文件”，而是建立一种：

```text
论文模块 -> 候选文件 -> 关键符号/代码片段 -> 证据 -> 置信度 -> 待确认问题
```

的证据链。

## 本阶段新增文件的分工

这一章新增了 4 个核心文件：

- `app/tools/search_tools.py`：负责在仓库里搜索文本和关键词。
- `app/prompts/mapping_prompt.py`：定义代码映射任务的 prompt。
- `app/nodes/code_search_node.py`：负责为每个论文模块生成候选代码文件和代码片段。
- `app/nodes/mapping_node.py`：调用 LLM 生成结构化 `ModuleMapping`。

这几个文件组成的主链路是：

- 论文模块生成关键词
- 关键词搜索仓库
- 统计候选文件
- 读取局部代码片段
- LLM 基于证据生成 mapping
- 输出 JSON 和 Markdown 报告

## 为什么不能直接让 LLM 读整个仓库

一个非常重要的设计选择是：不要把整个 repo 一口气塞给模型。

这样做有很多问题：

- 上下文太大，成本高。
- 噪声很多，模型容易被无关文件干扰。
- 一旦出错，很难判断是搜索错了、切片错了，还是映射错了。
- 很容易产生“看起来合理但没有证据”的幻觉。

V2 的设计是先用工具缩小候选范围，再让模型做判断。

所以这里的 LLM 不负责“从整个仓库里挖答案”，而是负责“在已经收集好的候选证据上做归纳和判断”。

## search_tools.py 的作用

`app/tools/search_tools.py` 是这个阶段的工具入口，核心有两个函数：

- `search_text()`：在 repo 中搜索某个查询词。
- `search_keywords()`：对多个关键词分别搜索并聚合结果。

`search_text()` 的作用是调用 `rg`，返回：

- 匹配文件路径
- 匹配行号
- 匹配文本内容

它提供的是“最原始的只读证据”。

`search_keywords()` 的作用则更接近“候选证据收集器”：

- 逐个关键词搜索
- 去重
- 给每条匹配补上命中的关键词

这使得后续节点不只是知道“搜到了什么”，还知道“是因为什么关键词搜到的”。

## 为什么关键词搜索是合理的第一步

论文模块通常会自带一些自然语言线索，比如：

- 模块名
- 论文术语
- `possible_keywords`

这些关键词虽然不保证完全准确，但足够作为第一轮召回手段。

这样做的价值是：

- 不需要一开始就理解完整代码语义。
- 可以快速缩小仓库范围。
- 如果多个关键词都命中同一文件，这个文件就更值得优先看。

这是一种非常典型的“先召回，再重排，再让模型判断”的设计。

## mapping_prompt.py 的角色

`MAPPING_PROMPT` 的作用不是简单说“帮我找代码”，而是明确告诉模型：

- 输入有哪些：
  - 论文模块
  - 搜索结果
  - 代码片段
- 你要做什么：
  - 判断这个模块可能对应哪些代码文件
- 输出时要遵守什么规则：
  - 每个候选必须给证据
  - 只靠文件名相似最多给 `medium`
  - 能对上类名、函数名、forward 逻辑、config 参数时才可以给 `high`
  - 不确定时写 `unresolved_questions`
  - 输出必须符合结构化 schema

也就是说，这个 prompt 不是在让模型自由发挥，而是在把它拉回“证据化判断”的轨道。

## code_search_node.py 在做什么

`code_search_node()` 是这一阶段非常关键的中间节点。

它的流程是：

1. 从 `state` 中读取：
   - `repo_path`
   - `method_modules`
2. 遍历每个论文模块。
3. 取模块名和 `possible_keywords` 组成搜索词列表。
4. 调 `search_keywords()` 搜索仓库。
5. 用 `_candidate_files_from_matches()` 根据命中频次给候选文件排序。
6. 对候选文件读取前 160 行左右的代码片段。
7. 把结果组织成 `code_search_results`。

这里最重要的设计点是：

- 不是把所有匹配全交给模型。
- 而是先做一轮轻量排序，再只抽取少量局部代码片段。

这样可以在成本和效果之间取得平衡。

## `_candidate_files_from_matches()` 为什么重要

这个辅助函数做的事情虽然简单，但思路很有代表性：

- 同一个文件如果被多个关键词反复命中，说明它更值得优先关注。

它用匹配频次来给文件打一个很粗的分数，然后选前几个文件。

这不等于最终结论，但很适合作为“候选文件选择器”。

换句话说，这里完成的是一个轻量 rerank，而不是最终语义判断。

## mapping_node.py 在做什么

`mapping_node()` 是把证据真正转化成结构化映射结果的节点。

它的流程是：

1. 从 `state` 中读取：
   - `method_modules`
   - `code_search_results`
2. 检查输入是否完整。
3. 创建聊天模型。
4. 使用 `with_structured_output(ModuleMapping)` 强制按 `ModuleMapping` 输出。
5. 对每个模块分别构造 prompt：
   - 模块信息
   - 搜索命中结果
   - 代码片段
6. 调模型生成该模块的映射结果。
7. 汇总所有模块的 mapping。
8. 输出：
   - `paper_code_mapping.json`
   - `paper_code_mapping.md`

这一步把“搜索结果”升级成了“带理由、带置信度、带未解决问题的结构化判断”。

## ModuleMapping 在这一阶段的意义

V2 依赖的结构化 schema 是 `ModuleMapping` 和 `CodeCandidate`。

其中：

- `CodeCandidate` 表示一个候选代码文件，包含：
  - `file_path`
  - `symbols`
  - `reason`
  - `evidence`
  - `confidence`
- `ModuleMapping` 表示一个论文模块的最终映射结果，包含：
  - `module_name`
  - `candidates`
  - `unresolved_questions`

这套设计的核心意义是：映射结果不是“我觉得像”，而是“我认为它像，证据是什么，信心有多高，还缺什么信息”。

## Markdown 报告为什么也要生成

这一阶段除了生成 JSON，还会生成 `paper_code_mapping.md`。

这样做的意义很大：

- JSON 方便后续节点继续消费。
- Markdown 方便人工快速复核。

人工复核时，你最关心的就是：

- 每个模块有没有候选文件。
- 这些候选是不是有证据支持。
- 置信度高低是否合理。
- 有哪些地方还需要进一步确认。

所以 Markdown 并不是附属品，而是“证据化映射”这一设计闭环中的重要一环。

## CLI 如何把整条链串起来

这一阶段的 CLI 入口是：

```bash
python -m app.main map-code data/paper.pdf /path/to/repo
```

它会依次调用：

- `paper_reader_node`
- `method_extractor_node`
- `repo_scan_node`
- `code_search_node`
- `mapping_node`

也就是说，V2 是第一次真正把：

```text
论文 -> 方法模块 -> 仓库地图 -> 代码候选 -> 结构化映射
```

整条链完整跑起来。

## 本阶段验收标准

这一阶段完成后，至少应该满足：

- 每个论文模块都能得到一组候选代码文件。
- 候选结果中能看到明确理由或证据。
- 置信度不应全部机械地写成 high。
- 找不到或不确定的信息要进入 `unresolved_questions`。
- 输出文件 `paper_code_mapping.json` 和 `paper_code_mapping.md` 都能生成。

如果这些都达到，说明项目已经具备了“从论文概念定位到代码实现”的关键能力。

## 这一阶段的关键收获

这一章最重要的收获，不是某个搜索函数，而是下面这些方法论：

- 不要让模型直接读整个仓库，先用工具缩小范围。
- 搜索、候选排序、局部阅读、结构化判断应分层完成。
- 映射结果必须带证据和置信度，否则不可复核。
- `unresolved_questions` 不是失败，而是降低幻觉的重要机制。
- V2 是后续实验计划、日志调试和人工审批的重要基础，因为这些阶段都依赖模块到代码的定位能力。

## 本阶段容易遇到的问题及解决思路

这一阶段实践时，最常见的问题集中在搜索工具依赖、候选噪声和结构化输出稳定性上。

### 1. `rg` 不存在，搜索阶段直接失败

典型报错是：

- `FileNotFoundError: [Errno 2] No such file or directory: 'rg'`

根因是：

- `search_text()` 依赖外部 `ripgrep`
- 当前运行环境的 `PATH` 里没有 `rg`

解决思路：

- 先确认运行程序的那个 Python 环境里能否找到 `rg`
- 确保 `ripgrep` 已安装并对当前 shell / debugger 可见
- 如果环境受限，可以考虑后续补一个 Python `Path.rglob()` 的 fallback

### 2. 搜到很多结果，但噪声很大

常见现象是：

- 同一个关键词命中大量无关文件
- 候选文件很多，但真正相关的只有少数

解决思路：

- 依赖 `possible_keywords` 提高搜索词质量
- 用命中频次先做轻量排序
- 只取前几个候选文件和有限代码片段给模型

### 3. 模型只根据文件名猜，不根据代码证据判断

这类问题通常表现为：

- 某个文件名很像论文模块名，就被高置信度选中
- 但候选里没有真正的类、函数或逻辑证据

解决思路：

- 在 prompt 中限制：只靠文件名相似最多 `medium`
- 明确要求引用类名、函数名、forward 逻辑、config 参数等证据
- 保留 `unresolved_questions`，不要强行断言

### 4. 结构化输出不稳定

实践中常出现：

- `ModuleMapping` 字段名不匹配
- `candidates` 结构不完整
- 输出自然语言说明而不是严格结构

解决思路：

- 使用 `with_structured_output(ModuleMapping)` 约束输出
- 必要时加强 prompt 中的字段说明
- 用 `include_raw=True` 查看原始返回，区分是模型没遵守 schema，还是本地校验失败

## 本阶段最重要的理解

V2 看起来是在“找代码”，但本质上是在建立一条可解释的证据链：

- 从论文模块出发
- 通过工具检索缩小范围
- 用代码片段补强证据
- 再让模型做结构化判断

如果这一阶段做扎实，后面的实验计划生成会更靠谱，因为它知道该参考哪些代码；日志 debug 也会更有方向，因为它知道某个模块大概率对应代码的哪一部分。

## 局限性

这一阶段仍然有一些天然局限：

- 搜索强依赖关键词质量，如果论文模块命名和代码命名差异很大，召回会下降。
- 读取的代码片段是有限的，可能看不到真正关键的实现位置。
- 命中频次是一种很粗的排序信号，不等于真实语义相关性。
- 只靠静态文本和片段判断，仍然无法完全替代人工复核。
- 对没有 `rg`、代码结构混乱或命名极不规范的仓库，效果会明显变差。
