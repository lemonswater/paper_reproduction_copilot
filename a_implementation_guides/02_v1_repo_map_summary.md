# 02. V1 代码仓库地图学习总结

## 这一阶段的目标

这一章的重点是把“读代码仓库”这件事，从盲目翻文件变成一个先扫描、再聚焦的流程：

- 输入本地代码仓库路径。
- 先生成仓库目录树，了解整体结构。
- 再按启发式规则把重要文件分类出来。
- 输出可复用的 `RepoMap`，为下一阶段的论文-代码映射做准备。

简单说，这一阶段解决的是“面对一个陌生 repo，先怎么快速建立全局视图”的问题。

## 本阶段新增了什么能力

相较于 V0 阶段的论文结构化阅读，V1 开始补足“代码侧认知”：

- 仓库目录扫描：快速看到项目的大致结构。
- 文件分类：找出 README、训练入口、评测入口、配置文件、模型文件、数据集文件和 loss 文件。
- 代码局部阅读工具：可以按行查看代码片段，也可以抽取 Python 符号。
- 仓库地图落盘：把扫描结果写入 `repo_map.json` 和 `repo_summary.md`。

这意味着项目不再只理解论文，还开始具备“理解代码实现长什么样”的基础能力。

## 本阶段新增文件的分工

这一章新增了 3 个核心文件：

- `app/tools/repo_tools.py`：负责扫描目录、列出文件和按规则分类。
- `app/tools/code_tools.py`：负责读取代码片段和提取 Python 符号。
- `app/nodes/repo_scan_node.py`：把扫描工具串成一个节点，产出结构化 `RepoMap`。

这几个文件共同形成了 V1 的主链路：

- 先扫目录树
- 再筛选重要文件
- 再把结果组织成统一结构
- 最后落盘供后续阶段使用

## 为什么先建代码地图

这一章最核心的思想是：不要让 Agent 一上来就盲读整个仓库。

如果没有地图，常见问题会很多：

- 仓库太大，直接读文件成本很高。
- 很多目录是无关产物，比如 `.git`、`outputs`、`wandb`。
- 训练、评测、配置、模型实现常常分散在不同位置，靠人工乱翻效率很低。
- 后续做论文-代码映射时，没有清晰的候选范围。

所以 V1 的目标不是“完整理解全部代码”，而是“先建立一个可导航的仓库索引”。

## repo_tools.py 的作用

`app/tools/repo_tools.py` 是这一阶段的基础扫描工具层，主要负责三件事：

- `get_file_tree()`：生成文本版的目录树。
- `list_files()`：递归列出仓库中的文件。
- `classify_repo_files()`：按启发式关键词对文件做初步分类。

其中 `IGNORE_DIRS` 定义了扫描时要跳过的目录，比如：

- `.git`
- `__pycache__`
- `.venv` / `venv`
- `node_modules`
- `outputs`
- `checkpoints`
- `wandb`

这样做的意义是避免把注意力浪费在无关文件上。

## 文件树为什么重要

`get_file_tree()` 的价值在于：它先给出一个“仓库长什么样”的粗视图。

比如你不需要一开始就读 `train.py` 的具体实现，但你需要先知道：

- 顶层有没有 README
- 有没有 `configs/`
- 模型相关代码集中在哪个目录
- 数据处理是不是单独放在 `datasets/` 或 `data/`

目录树是一种很低成本但高信息密度的表示形式，特别适合陌生仓库的第一轮摸底。

## 启发式分类在做什么

`classify_repo_files()` 并不理解代码语义，它靠的是“路径名和文件名里有没有某些关键词”。

它会把文件归到这些类别里：

- `readme_files`
- `train_entries`
- `eval_entries`
- `config_files`
- `model_files`
- `dataset_files`
- `loss_files`

例如：

- 文件名里有 `train` 或 `finetune`，就可能归入训练入口。
- 路径里有 `eval`、`test`、`infer`，就可能归入评测入口。
- 后缀是 `.yaml`、`.json`、`.toml` 等，或路径里带 `config`，就可能归入配置文件。

这一层不是为了“百分之百准确”，而是为了先快速缩小后续重点阅读范围。

## code_tools.py 的作用

`app/tools/code_tools.py` 是为后续细粒度代码分析准备的工具，主要有两个函数：

- `read_file_slice()`：按行读取代码片段，并保留行号。
- `extract_python_symbols()`：用 AST 提取 Python 类名、函数名和对应行号。

这里的思路很重要：

- V1 阶段先不让 Agent 一次读完整仓库代码。
- 但要预留“只看某一段代码”以及“只看某个文件有哪些定义”的能力。

也就是说，`code_tools.py` 更像是“仓库地图建立之后，用来进一步放大查看局部区域的工具”。

## 为什么要提取符号

`extract_python_symbols()` 使用 Python 的 `ast` 做静态解析，而不是靠正则去猜。

它能抽出：

- class 定义
- function 定义
- async function 定义

并记录名字和行号。

这样做的价值是：

- 后续定位论文模块对应代码时，可以先看哪些类和函数值得关注。
- 比直接把整文件送给模型更省上下文。
- 为 V2 阶段的候选代码映射提供更结构化的线索。

## repo_scan_node.py 如何串联整条链

`app/nodes/repo_scan_node.py` 是 V1 的主节点，它把前面的工具组合起来。

它的流程是：

- 从 `state` 中读取 `repo_path`
- 生成目录树 `tree`
- 获取分类结果 `classified`
- 合并出 `important_files`
- 构造 `RepoMap`
- 把结果写入 `outputs/repo_map.json` 和 `outputs/repo_summary.md`
- 再把扫描结果回写到 `state`

这一层体现了节点化设计的好处：工具函数只关心局部能力，节点负责把这些能力编排成可复用的工作流步骤。

## RepoMap 在这一阶段的意义

`RepoMap` 是这一阶段最核心的结构化输出。

它至少包含这些信息：

- 仓库路径
- README 列表
- 训练入口
- 评测入口
- 配置文件
- 模型文件
- 数据集文件
- loss 文件
- important_files

这意味着后续阶段不需要重新遍历整个仓库，而是可以直接消费 `repo_map` 作为代码侧的高层索引。

## 输出文件的设计

这一阶段最终会生成两个输出文件：

- `outputs/repo_map.json`
- `outputs/repo_summary.md`

它们承担的角色不同：

- `repo_map.json`：给程序和后续节点读取，强调结构化。
- `repo_summary.md`：给人快速浏览，强调可读性。

这和 V0 阶段同时产出结构化结果与可查看结果的思路是一致的。

## CLI 如何把仓库扫描跑起来

在 `app/main.py` 中新增的 `scan-repo` 命令，是这一阶段的运行入口：

```bash
python -m app.main scan-repo /path/to/paper-official-repo
```

它的逻辑很直接：

- 构造最小 `state`
- 调用 `repo_scan_node()`
- 打印扫描完成信息和输出文件路径

这样 V1 阶段也有了独立、可验收的 CLI 入口，而不是只剩一组零散工具函数。

## 本阶段验收标准

这一阶段完成后，至少应该满足：

- 可以对指定 repo 生成目录树。
- 可以忽略无关目录，不把缓存和输出目录混进结果里。
- 可以初步识别 README、train、eval、config、model、dataset、loss 相关文件。
- 可以把这些结果组织成 `RepoMap`。
- 可以输出 `repo_map.json` 和 `repo_summary.md`。

如果这些都跑通，说明项目已经具备了“先建代码地图，再决定读哪里”的能力。

## 常见坑

这一章也提醒了几个很容易踩的坑：

- 目录扫描必须忽略 `.git`、`outputs`、`checkpoints`、`wandb` 等无关目录。
- 启发式分类本身可能误判，所以它是“候选集生成”，不是最终语义理解。
- 仓库很大时，不要一口气把所有代码内容读进模型，只保留路径、分类和符号信息。

这些限制不是缺点，而是这个阶段刻意保持轻量化的设计选择。

## 关键收获

这一章最重要的收获是“仓库理解也要先结构化，再深入”：

- 不要让 Agent 直接盲读整个 repo。
- 先建立目录树和文件分类，再决定优先看哪些文件。
- 启发式规则虽然不完美，但能高效生成高价值候选集。
- 代码片段读取和符号提取，是后续细粒度分析的过渡层。
- `RepoMap` 是后续论文-代码映射的重要输入，而不是一次性的中间结果。

如果这一阶段做扎实，后面做 V2 的论文模块到代码候选映射时，就不会从整个仓库里无头苍蝇式地找实现。

## 局限性
- 只能都本地仓库，无法直接网上搜索
- 无法直接从论文中提取github链接或论文主页
- 只能通过文件名字分类，没办法通过代码进一步划分
