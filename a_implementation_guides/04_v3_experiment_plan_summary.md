# 04. V3 复现实验计划生成学习总结

## 这一阶段的目标

这一章的重点是把“知道论文讲了什么、代码大概在哪”进一步推进到“接下来应该怎么复现”。

输入不再只是论文或仓库，而是前面几个阶段已经整理好的结构化结果：

- `paper_summary`
- `repo_map`
- `paper_code_mapping`

输出则是：

```text
outputs/experiment_plan.json
outputs/experiment_plan.md
```

简单说，这一阶段解决的是“如何把分散在论文、README、配置和代码映射中的信息，整理成一个人可以照着执行的复现实验计划”。

## 本阶段新增了什么能力

相较于 V0 的论文结构化阅读和 V1/V2 的代码侧定位，V3 开始真正面向“执行”：

- 定义实验计划专用 schema。
- 把实验计划拆成环境、数据、训练、评估四类步骤。
- 单独抽出可执行命令，并标记来源与风险。
- 把不确定项集中写入 `unresolved_questions`。
- 生成既适合程序消费、也适合人阅读的计划文件。

这意味着项目不再只停留在“分析论文与代码”，而开始具备“给出下一步行动方案”的能力。

## 为什么实验计划也要结构化

如果只是让模型输出一段“建议你先装环境，再训练模型”的自然语言，问题会很多：

- 没法区分哪些步骤来自论文，哪些来自 README，哪些只是模型推断。
- 命令的可信度和风险等级不清楚。
- 不确定项容易混在叙述里，后续难以追踪。
- 后面做审批、恢复、执行和调试时，没有统一的数据接口。

所以这一阶段不是单纯生成说明文，而是要生成一个可验证、可落盘、可复用的 `ExperimentPlan`。

## app/schemas.py 在这一阶段的作用

这一章给 `schemas.py` 增加了三个关键结构：

- `ExperimentStep`
- `RunCommand`
- `ExperimentPlan`

其中：

- `ExperimentStep` 表示一个实验步骤，记录顺序、名称、具体动作、来源、证据、风险和完成状态。
- `RunCommand` 表示一条建议执行的命令，单独记录命令本身、工作目录、来源、风险等级和理由。
- `ExperimentPlan` 则是整个实验计划的顶层容器，把流程拆成：
  - `environment_steps`
  - `data_steps`
  - `train_steps`
  - `eval_steps`
  - `run_commands`
  - `risks`
  - `unresolved_questions`

这套设计的价值在于：实验计划从一开始就被定义成“结构化执行清单”，而不是一段模糊建议。

## 为什么要把步骤分成四类

实验复现通常不只是“运行一个训练命令”。

实际流程往往至少包括：

- 环境准备：安装依赖、检查 Python / CUDA / PyTorch 版本。
- 数据准备：下载数据、整理目录、预处理文件。
- 训练流程：修改配置、运行训练脚本、设置超参数。
- 评测流程：加载 checkpoint、执行推理、收集指标。

把这些步骤拆开有几个好处：

- 结构更清晰。
- 每一类步骤都可以单独检查和补充。
- 后面如果接入审批、执行或失败恢复，也更容易在状态图里单独处理。

## RunCommand 为什么要单独建模

这一章里一个很重要的工程化意识，是把“步骤描述”和“命令建议”区分开。

原因是：

- 不是每个步骤都一定对应一条可直接执行的命令。
- 命令往往需要额外标记 `cwd`、`source` 和 `risk_level`。
- 后续做 human-in-the-loop 时，命令是高风险对象，必须被单独识别出来。

所以 `RunCommand` 的出现，不只是为了方便展示，而是为后面的安全执行和审批打基础。

## app/prompts/plan_prompt.py 的角色

`EXPERIMENT_PLAN_PROMPT` 的作用不是简单告诉模型“帮我生成实验计划”，而是把模型约束到一个更可靠的输出模式。

它至少要传递这几层信息：

- 输入来源是什么：
  - 论文摘要
  - 仓库地图
  - 论文-代码映射
  - 用户实验目标
- 输出要求是什么：
  - 不要自动执行命令
  - 每条命令都要标记来源
  - 不确定的信息要进入 `unresolved_questions`
  - 高风险动作要标记风险

换句话说，这个 prompt 的真正任务，是把“计划生成”从泛泛建议，变成一个有数据边界、有风险意识、有证据来源的结构化抽取问题。

## app/nodes/experiment_plan_node.py 在做什么

这一阶段的主节点是 `experiment_plan_node()`。

它的大致流程是：

1. 从 `state` 中读取：
   - `paper_summary`
   - `repo_map`
   - `paper_code_mapping`
2. 检查这些输入是否齐全。
3. 构造聊天模型。
4. 使用 `with_structured_output(ExperimentPlan)` 强制模型按 `ExperimentPlan` 输出。
5. 把前面阶段的结构化结果序列化成 JSON 字符串，填入 prompt。
6. 调用模型生成实验计划。
7. 把结果同时写成：
   - `experiment_plan.json`
   - `experiment_plan.md`
8. 再把 `experiment_plan` 和 `run_commands` 回写到 `state`。

这说明 V3 并不是一条独立功能，而是把前几个阶段的结果真正串起来，形成一个更接近“可执行决策”的节点。

## markdown 渲染为什么重要

这一步除了保存 JSON，还会生成 `experiment_plan.md`。

这个设计很实用，因为：

- JSON 适合程序继续处理。
- Markdown 适合人快速检查。

`_render_steps()` 和 `_render_plan_markdown()` 的作用就是把结构化计划渲染成一份更容易浏览的报告，让你可以快速看到：

- 当前目标是什么
- 每一类步骤有哪些
- 推荐执行哪些命令
- 哪些问题还没确认

这和前几个阶段“同时输出机器可读结果和人类可读结果”的思路是一致的。

## CLI 如何把整条链串起来

这一阶段的 CLI 入口是在前面 `map_code` 的基础上再接一个节点。

命令形式是：

```bash
python -m app.main plan-experiment data/paper.pdf /path/to/repo --goal "复现论文 main result"
```

它做的事情是：

- 先跑论文阅读
- 再跑仓库扫描
- 再跑论文-代码映射
- 最后跑实验计划生成

这意味着 V3 其实是第一次让“论文 -> 代码 -> 行动方案”整条链在 CLI 层面闭环起来。

## 本阶段验收标准

这一阶段完成后，至少应该满足：

- 可以生成 `experiment_plan.json` 和 `experiment_plan.md`。
- 计划中能区分环境、数据、训练、评估四类步骤。
- 命令必须带来源标记，而不是只写一条裸命令。
- 不确定的路径、参数、checkpoint 等信息会进入 `unresolved_questions`。
- 有风险的动作会被标记，而不是直接执行。

如果这些都满足，就说明项目已经从“理解论文和代码”进化到了“给出可操作复现方案”。

## 这一阶段的关键收获

这一章最重要的收获，不是某个具体函数，而是以下几条工程思维：

- 实验计划不应该是自然语言闲聊，而应该是结构化对象。
- 命令建议必须带来源，否则后续无法判断可信度。
- 不确定信息不能被悄悄吞掉，应该被显式记录为 `unresolved_questions`。
- 风险要在计划阶段就显式暴露，而不是等执行时再临时发现。
- 前几个阶段的结果只有在这一章被组织成行动方案后，才真正体现出链路价值。

## 本阶段容易遇到的问题及解决思路

这一阶段实践时，常见问题主要集中在 schema 对齐、prompt 约束和结构化输出稳定性上。

### 1. 模型返回自然语言计划，而不是 JSON

典型现象是：

- 返回 `# Experiment Plan` 这种 Markdown 标题
- 返回项目符号列表
- 甚至返回 `{plan}` 这种占位符文本

这会导致 `ExperimentPlan` 的结构化解析失败。

解决思路：

- 强化 prompt，明确要求只输出一个合法 JSON 对象。
- 禁止输出 Markdown、解释性文字和占位符。
- 显式写出顶层字段和子对象字段。

### 2. 上下文虽然齐了，但计划仍然不可靠

前面阶段给出的 `paper_summary`、`repo_map`、`paper_code_mapping` 只是候选信息，不代表所有实验细节都已确定。

所以模型很容易在：

- batch size
- GPU 数量
- checkpoint 路径
- 数据目录
- 依赖版本

这些地方产生“看起来合理但实际是猜的”内容。

解决思路：

- Prompt 中明确要求：不确定就写 `unresolved_questions`。
- 把 `need_confirm` 当成允许的输出状态，而不是失败。

## 本阶段最重要的理解

V3 看起来是在“生成实验计划”，但本质上是在做一件更重要的事：

- 把分析结果转化为行动方案
- 把自然语言建议转化为结构化决策对象
- 把后续可能的执行风险提前暴露出来

如果这一阶段做扎实，后面的 LangGraph、审批、恢复、日志 debug 和评测，都会有更稳的输入基础，因为它们都依赖这份 `ExperimentPlan`。

## 局限性

这一阶段仍然有几个天然局限：

- 它生成的是“计划”，不是“自动执行”。
- 如果前面阶段的论文摘要或代码映射本身不准，计划质量也会受影响。
- 对命令、路径和依赖的判断，仍然高度依赖论文与仓库中是否有明确证据。
- 对于没有 README、配置混乱或脚本命名不规范的仓库，计划里的 `need_confirm` 和 `unresolved_questions` 会明显变多。
